数据层：
Redis  —— 运行时权威状态（精灵体力 / 限流计数 / 活跃池，TTL）
MySQL  —— 异步持久快照（业务账本 / 事件表 / 快照窗口 / 审计）
MQ     —— 事件总线（RabbitMQ/Kafka，事件信封携带版本元数据）
关键设计决策：
・运行时权威状态在 Redis，MySQL 仅做异步持久快照；Redis 未命中回填策略见 §2.4。
・外部异源输入全部经 gate-service 统一校验闸门。
・audit-service 独立 topic，不复用业务主链路。

・事件信封统一携带 event_id + snapshot_version + trace_id，与 payload 隔离。

2.2 Redis Key 设计（限流 key 绑快照版本）

表格

| Key 模式 | 用途 | TTL |
| --- | --- | --- |
| spirit:{uid} | 精灵运行时状态（体力权威） | 关联 48h |
| spirit:stamina:lock:{uid} | Lua 原子校验 / 扣减 | 短 TTL |
| limit:wander:{uid}:{snapshot_version} | 精灵溜达计数 | 随版本废弃 |
| limit:pair:{min(uidA,uidB)}:{max(uidA,uidB)}:{snapshot_version} | 两两互访计数（有序） | 随版本废弃 |
| limit:bp_recover:{uid}:{snapshot_version} | 沸点恢复体力上限计数 | 随版本废弃 |
| limit:return:{uid}:{snapshot_version} | 矿脉返还上限计数 | 随版本废弃 |
| active_pool:{snapshot_version} | 活跃用户池（Set） | 随版本废弃 |
| mailbox:count:{uid} | 信箱包裹数上限 | 48h |
| snapshot:current | 当前快照版本 | 常驻 |
| lock:active_pool_refresh | 活跃池刷新分布式锁（Redisson） | lease 30s |

规则：
・限流 key 一律携带 snapshot_version，新窗口版本变化即生成新 key，旧 key 自然废弃，不单纯依赖 TTL。
・pair key 必须 min (uidA,uidB) 在前、max 在后，保证 A→B 与 B→A 命中同一 key。

2.3 MQ 事件信封规范

```
{
  "event_id": "uuid-v4",
  "event_type": "mining_success | passive_return | spirit_wander | mailbox_write | spirit_energy_change | bp_standardized | ...",
  "snapshot_version": "SNP-1735689600",
  "trace_id": "uuid-v4",
  "producer": "note-service",
  "occurred_at": "ISO8601",
  "payload": {}
}
```

・幂等键统一为 event_id；trace_id 仅追踪，不得作为幂等键。
・元数据与 payload 分离，编码约束禁止在 payload 解析时混入执行逻辑。
・消费时 snapshot_version 不匹配当前窗口 → 拒绝并上报对应审计事件（如 mining_success_drop）。

2.4 Redis 故障回填策略
・Redis 未命中 → 读 MySQL spirit_state 回填。
・回填时 state 强制 IDLE，体力取 min (MySQL.energy, 5)。
・回填事件上报 audit cache_refill。
・回填不得让体力倒挂（若 Redis 存在更高体力，以 Redis 为准，不回填覆盖）。

三、服务职责与权限原子化（六维约束）
3.1 note-service（矿洞系统）

1. 核心职责：公开笔记→矿山映射、高光碎片抽取、私密硬锁、挖矿成功事件输出。
2. 私有状态：矿山映射表、私密锁名单、碎片原始内容、挖矿成功历史标记。
3. 可公开状态：可挖矿山清单、高光碎片、挖矿成功事件。
4. 允许接收输入：笔记发布 / 修改 / 私密化事件（经 gate 校验）。
5. 允许发出输出：矿山状态变更事件、碎片供给、mining_success_event（带快照）。
6. 越界黑名单：禁止修改用户原始笔记；禁止泄露私密笔记；禁止跨用户读笔记；禁止直接写积分账本；禁止输出未做长度 / 畸形校验的碎片内容。

3.2 gate-service（异源校验闸门）

1. 核心职责：外部异源输入二次校验、有效沸点判定、标准化事件输出。
2. 私有状态：校验规则、有效沸点判定逻辑、闸门配置。
3. 可公开状态：标准化事件（带快照版本）。
4. 允许接收输入：掘金笔记元数据、沸点原始流、掘金敏感词 API 返回、用户 UGC。
5. 允许发出输出：标准化沸点事件、标准化笔记事件、标准化吐槽事件。
6. 越界黑名单：禁止透传原始沸点载荷；禁止透传畸形 / 超限碎片；拒绝 payload 超限事件。

3.3 spirit-service（精灵系统）

1. 核心职责：精灵实例状态机、体力、溜达行为。
2. 私有状态：状态机内部态、体力值、心情、背包、今日溜达计数。
3. 可公开状态：当前状态、战利品摘要、体力值。
4. 允许接收输入：溜达任务派发事件、挖矿判定结果、gate 输出的有效沸点标准化事件。
5. 允许发出输出：挖矿任务请求、回归提示、体力变更事件。
6. 越界黑名单：禁止直接写漂流信箱；禁止修改笔记 / 沸点原始数据；禁止解析原始沸点内容；禁止自行判定有效沸点。

3.4 defense-service（防御系统）

1. 核心职责：48h 沸点结算、种草积分账本、草量防御值、矿脉被动返还积分。
2. 私有状态：积分账本、结算快照、矿脉挖矿成功事件记录（含快照版本）。
3. 可公开状态：当前种草积分、草量防御值。
4. 允许接收输入：沸点标准化统计事件、矿洞挖矿成功事件（带快照）。
5. 允许发出输出：积分变更事件、草量更新事件、积分返还落库 ACK。
6. 越界黑名单：禁止读写用户笔记原文；禁止覆盖结算快照版本；禁止直接接收原始沸点载荷。

3.5 mailbox-service（漂流信箱）

1. 核心职责：吐槽 / 碎片包裹匿名存取、48h 过期销毁、阅后即焚。
2. 私有状态：信箱载荷、产生时间戳、TTL 标记（不存发送方明文 user_id）。
3. 可公开状态：接收方可读的匿名消息。
4. 允许接收输入：精灵投递包裹（带 ACK）、用户操作（点赞 / 踩 / 收入笔记 / 即焚）。
5. 允许发出输出：写入成功 ACK、消息展示事件。
6. 越界黑名单：禁止显示发送方实名；禁止超期保留数据；禁止评论 / 私信。

3.6 scheduler（48h 节拍器 / 派发器）

1. 核心职责：窗口推进、批量结算、体力回满、活跃池刷新、任务派发、过期清理。
2. 私有状态：快照窗口、节拍执行进度、分布式锁状态。
3. 可公开状态：窗口版本、执行状态摘要。
4. 允许接收输入：各服务状态变更事件、定时触发。
5. 允许发出输出：结算事件、任务派发事件、窗口状态变更事件。
6. 越界黑名单：禁止直接写业务账本（只发事件）；禁止绕过限流直接派发；禁止执行中覆盖已关闭窗口。

3.7 audit-service（审计）

1. 核心职责：独立通道承接经济事件与异常上报、降采样、告警指标。
2. 私有状态：审计明细、采样配置。
3. 可公开状态：审计查询结果。
4. 允许接收输入：全服务 audit 事件。
5. 允许发出输出：告警、审计查询响应。
6. 越界黑名单：禁止反向写业务状态；禁止参与业务决策。

四、精灵行为状态机与并发防护
4.1 状态机

```
IDLE → WANDERING → CHECKING → MINING → RETURNING → IDLE
                 ↘(超时>5s) ABORT ↙
```

・任何阶段超时（CHECKING/MINING > 5s）强制 ABORT → RETURNING → IDLE，杜绝卡死中间态。
・状态机单流转，禁止跨状态跳转。
・前端皮肤层仅访问 view-model，禁止修改业务状态。

4.2 Lua 原子脚本（取出执行前校验 + 扣减）

```
-- KEYS[1] = spirit:state:{uid}
-- ARGV[1] = snapshot_version
-- ARGV[2] = wander_limit (默认 5)
-- ARGV[3] = task_id
local state = redis.call('HMGET', KEYS[1], 'stamina', 'wander_count', 'state')
local stamina = tonumber(state[1] or 0)
local count   = tonumber(state[2] or 0)
if stamina <= 0 then
  return {0, 'NO_STAMINA'}
end
if count >= tonumber(ARGV[2]) then
  return {0, 'WANDER_LIMIT'}
end
redis.call('HINCRBY', KEYS[1], 'stamina', -1)
redis.call('HINCRBY', KEYS[1], 'wander_count', 1)
redis.call('HSET', KEYS[1], 'state', 'WANDERING', 'last_task', ARGV[3])
return {1, stamina - 1}
```

・派发时只校验不扣体力；取出执行时原子扣减。
・失败则任务 ABORT，不进入 WANDERING，不产生负体力，上报 audit task_abort。
・任务过期直接丢弃并上报审计。

4.3 MINING 私密二次校验
MINING 开始前查 MySQL 主库：is_private=0 AND status=ACTIVE。不满足则 ABORT，不写碎片，可留吐槽包裹。封堵 “置私密与挖矿并发窗口”。

4.4 MQ 消费幂等
・幂等键 = event_id，唯一键挡重。
・防重不防丢：重复投递被幂等拦截；丢失事件只进 audit，不业务重试。

五、安全与风控
5.1 UGC 审核前置
・吐槽必须过掘金敏感词审核 API + 本系统二次最小校验（长度、基础格式）。
・不通过拦截在本地，不进入下游。

5.2 有效沸点判定收口
・判定逻辑统一放在 gate-service；输出带快照版本的标准化沸点事件。
・原始沸点载荷不下透；种草积分与体力恢复两套业务消费同一带版本事件源。

5.3 防骚扰限流（48h 节拍统一）
・单精灵 48h 溜达上限 5 次（与体力上限联动）。
・同一对用户 48h 内最多互访 1 次，pair key 有序。
・全部限流 key 绑定 snapshot_version。

5.4 隐私隔离
・实名信息、浏览记录严禁经精灵泄露。
・mailbox-service 不存发送方明文 user_id，只存 HMAC‑SHA256 (server_key, sender_uid)，可审计不可展示。

5.5 数据销毁（统一 48h）
・漂流吐槽与碎片保留 48h；“阅后即焚” 或超时后物理删除，绝不永久留存。
・48h 内未领取漂流，过期即焚，不通知、不补偿。

5.6 碎片异源载荷校验
・碎片抽取设最大长度硬上限（默认 500 字），超限直接截断 / 丢弃并上报 audit fragment_oversize_reject。
・过滤畸形 HTML / 脚本载荷，拒绝危险载荷向下游传递，防 XSS。
・校验主体为 gate‑service，禁止业务模块自校验。

---

六、48h 节拍器流程（分步执行 + 断点续跑）
6.1 快照版本生成规则（定死）

```
唯一生成方：scheduler 在 Step1/Step2 生成并写入 snapshot_window，同时广播。
只读方：其余服务只读事件信封中的 snapshot_version，禁止自行计算。
公式（兜底一致性）：
  window_start = floor(epoch_ms / 172800000) * 172800000
  snapshot_version = "SNP-" + window_start_unix
跨窗口事件处理：消费时 snapshot_version != 当前窗口 → 拒绝并上报对应审计事件。
```

6.2 节拍流程拆分

```
Step1 关闭旧窗口
Step2 新建快照窗口
Step3 结算沸点（限速，调用掘金上游）
Step4 体力回满至 5，wander_count_48h=0，stamina_recovered_48h=0
Step5 刷新 active_pool（带分布式锁）
Step6 清理过期信箱（物理删除 ttl_at <= now()）
Step7 打开新窗口
```

・每步执行完成，写入 snapshot_window.exec_step + step_ack_map。
・进程崩溃后，下次调度从断点继续，不从头完整重跑。
・任一步失败：记录 audit scheduler_step_fail，已完成的步骤不重复执行。

6.3 重试边界声明（P0‑4）

```
重试边界：
- 基础设施级断点续跑（仅限 scheduler 节拍器 7 步流程）：允许。进程崩溃后从 exec_step 续跑，已 ACK 步骤不重复。
- 业务事件级（积分返还、体力变更、信箱写入、沸点消费）：禁止重试。失败即 audit，丢弃不补偿。
- 判定口诀：scheduler 内部步骤可续跑；跨服务业务事件只防重、不重试。
- 跨窗口版本不匹配不属于业务异常，按上面矩阵做丢弃 / 归入新窗口；**依然禁止业务层重试，仅靠审计记录事件原始去向。**
```

6.4 活跃池刷新（分布式锁）
・Redisson RLock，tryLock (wait=0, lease=30s)。
・锁竞争失败直接放弃本轮刷新，等待下一个节拍，上报 audit active_pool_refresh_fail。
・杜绝多 scheduler 实例无锁写乱活跃用户池。

6.5 上游接口熔断降级
・对掘金笔记、沸点、敏感词接口配置熔断器。
・上游不可用时，本窗口部分任务跳过，记录 audit upstream_breaker_open，等待下一个 48h 窗口。
・不阻塞整个系统崩溃，降级而非停滞。
・产品确认项：熔断窗口跳过，用户少一轮种草 / 体力恢复，接受不补偿（需产品签字）。

## 6.6 跨窗口事件归属、处理矩阵 & 经济闭环设计意图

### ① 为什么需要（重要程度：P0）

48h 快照窗口切换时刻存在时间缝隙，事件产生时刻、MQ 投递消费时刻会落在不同窗口。
原方案仅描述 “版本不匹配直接拒绝”，缺失拒绝之后事件归属去向；容易出现：

- 挖矿、积分相关事件无明确归宿，审计只能看到被拒绝，但不知道这条事件应当归属于旧窗口还是直接丢弃；
- 团队容易对微循环经济产生误解，把「挖矿获取积分增益」当成程序 Bug；
- 没有矩阵，开发人员凭主观写判断逻辑，各服务处理不一致，引入隐性 bug。

### ② 经济闭环的设计意图说明（厘清：越挖越强是特性，非 bug）

> 
> **特性定位：「越挖越强」属于产品刻意设计的微循环正向反馈特性，不是程序缺陷。**
> 业务逻辑：笔记被他人挖矿成功 → 矿主获得被动返还种草积分 → 消耗积分提升笔记草量防御，降低后续被挖矿概率。
> 完整链条拆解：

1. 用户产出公开知识笔记（知识输出）；
2. 被其他精灵挖矿成功，代表这份内容产生社区互动价值；
3. 系统给予少量种草积分作为产出激励；
4. 用户拿积分给笔记加高防御，保护自己这份知识资产少被掠夺。

**边界约束（防止特性走向恶性通胀）：**

- 设置单用户 48h 矿脉返还积分硬上限，封顶，无限叠加被扼制；
- 积分来源仅限「自己笔记被别人挖」，**自己出去挖矿不会给自己产生返还积分**；
- 积分只能用于增加笔记防御，不能兑换体力、不能流通交易，没有代币化。

> 
> 误区提示：
> ❌错误理解：挖的越多，我无敌。
> ✔正确理解：**输出越多高质量公开笔记，获得有限防御 buff；buff 有上限，无法无限膨胀。是对知识输出者的小额防御奖励，不是战斗力无限膨胀。**

### ③ 事件信封 snapshot_version 不匹配完整处理矩阵

> 
> 判定前提：
> 
> 
> - `event_sv`：事件自身携带的快照版本（事件产生那一刻的窗口）
> - `current_sv`：节拍器此刻对外广播的当前快照版本
> - 窗口已经关闭定义：`event_sv`对应的`snapshot_window.settle_status = DONE`

表格

| 事件类型 | 场景 | 处理动作 | 拒绝后归属去向 | 审计事件标识 |
| --- | --- | --- | --- | --- |
| mining_success（挖矿成功事件） | event_sv == current_sv | 正常消费，执行积分返还 | - | - |
| mining_success | event_sv 窗口已关闭（旧窗口，DONE） | **直接丢弃，不归属新窗口** | 这条挖矿发生在上一个已经结算完毕的周期，周期已归档，不再执行返还；事件彻底丢弃 | `mining_success_drop` |
| passive_return（积分返还） | event_sv == current_sv | 正常消费落库 | - | - |
| passive_return | event_sv 窗口已关闭 | 直接丢弃 | 旧窗口结算闭环完成，不二次补发返还 | `passive_return_ack_fail` |
| bp_standardized（标准化沸点事件） | event_sv == current_sv | 正常消费，计入本窗口积分、体力恢复 | - | - |
| bp_standardized | event_sv 窗口已关闭 | **允许归属新窗口消费** | 沸点行为真实发生，只是消费落在窗口切换缝隙，归入当前最新窗口统计；**受 48h 恢复上限约束，不会无限累加** | `bp_event_roll_new_window` |
| spirit_energy_change（体力变更） | event_sv == current_sv | 正常消费 | - | - |
| spirit_energy_change | event_sv 窗口已关闭 | 直接丢弃 | 体力是窗口周期资源，过期作废，不回溯补体力 | `spirit_energy_drop` |
| mailbox_write（信箱投递） | event_sv == current_sv | 正常执行写入信箱 | - | - |
| mailbox_write | event_sv 窗口已关闭 | **允许归属新窗口执行投递** | 投递行为只做匿名消息存储，不属于周期结算经济数据；消息允许跨窗口落地，TTL 依旧 48h 从写入时刻开始计时 | `mailbox_event_roll_new_window` |

#### 矩阵执行总规则（编码必须遵守）

1. **经济结算类事件（挖矿成功、积分返还、体力变更）：旧窗口一旦标记 DONE 归档，一律丢弃，绝不回溯旧周期做补发。**

> 
> 契合产品 “随缘，错过就错过”，不做历史补偿。

2. **纯行为载体事件（沸点统计、信箱投递）：无历史结算副作用，可以归属当前新窗口执行，但依旧要受对应窗口上限硬约束，防止刷量。**
3. 所有发生版本不匹配的分支，**无论丢弃还是归入新窗口，100% 必须上报 audit‑service 审计，不能静默吞掉事件。**
